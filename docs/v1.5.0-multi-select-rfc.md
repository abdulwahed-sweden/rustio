# RFC: Multi-Select for Admin Tables (v1.5.0)

**Status:** Accepted, deferred to v1.5.0
**Authors:** Abdulwahed Mansour, Claude (collaboration)
**Date:** 2026-05-01
**Targets release:** v1.5.0

---

## Summary

Add a generic, id-based multi-select system to admin list views. Selection works
across every model without per-model code, surfaces a contextual action bar
when one or more rows are selected, and ships with placeholder actions until a
backend (`/admin/<model>/_action`) lands in a follow-up phase.

This RFC is the design contract for v1.5.0. It does NOT specify implementation
order; the implementing phase will turn this into Parts A–F.

---

## Goals

- Selection model is **purely id-based** — no field-name logic, generic across
  all models.
- UI: checkbox column (first column), header select-all, visible "selected"
  row state, contextual action bar.
- Behaviour preserves existing row-link navigation. Clicking a row's primary
  link still navigates; clicking the checkbox does not.
- Page-scoped selection (current page only). Cross-page selection is out of
  scope for v1.5.0.
- No-JS environment still toggles checkboxes natively. Action-bar count UI
  requires JS; the future submit path uses a real `<form>` so non-JS users can
  still submit.

## Non-goals (explicitly deferred)

- Cross-page selection persistence (`localStorage` / hidden inputs).
- Modal-based confirmation flows.
- Per-row drag-select / shift-click range selection.
- Saved selection sets / "remember selection" UX.
- Bulk actions wiring (`/admin/<model>/_action`) — separate phase.

---

## Pre-existing context

- `ListCtx.bulk_actions_enabled: bool` already exists in
  `rustio-core/src/admin/render.rs` (currently hardcoded `false`). Phase 6a
  scaffolded it specifically for this feature: *"Templates hide the action bar
  when this is `false` so we don't ship UI that 404s on submit."*
- Row primary cell already uses `<a class="row-link">` for navigation (no
  row-level click handler exists).
- `field.kind == "checkbox"` is already used for boolean *data* cells —
  the new selection column must use a different attribute (`.select-cell`).
- v1.4.1 hover work added `transition: background 120ms ease;` on
  `.table tbody td` — selection state animates for free.
- `--rio-accent-bg: #fff4ed` and `--rio-accent-border: #fed7aa` already exist
  in the token table — no new tokens needed for the selected state.

---

## Decisions (locked at RFC time)

1. **`selectable` flag — yes**, but only when implementation begins. New
   `ListCtx.selectable: bool` (default `true` once shipped). Keep
   `bulk_actions_enabled` for the *real* action wiring later.
2. **Form wrapper — no, not now.** Do not add inactive forms before backend
   exists. The form wraps the table only when the backend lands.
3. **Bulk delete confirmation — option (c).** Submit selection to a
   confirmation page that lists what's about to be deleted, then a final
   confirm submit performs the action. Matches the existing
   `/admin/users/<id>/delete` pattern. No native `confirm()`. No modals.
4. **Static JS — separate registry.** Embed via a new `EMBEDDED_STATIC_JS`
   table, not the existing `EMBEDDED_TEMPLATES` (which is for minijinja
   sources only).

## 1. UI structure

### Selection column (first column)

Header:

```html
<th scope="col" class="select-cell">
  <input type="checkbox" class="select-all"
         {% if not rows %}disabled{% endif %}
         aria-label="Select all rows on this page">
</th>
```

Body (one per row), inserted before the `{% for field in fields %}` loop:

```html
<td class="select-cell">
  <input type="checkbox" class="row-select"
         name="selected_ids[]" value="{{ row.id }}"
         aria-label="Select row {{ row.id }}">
</td>
```

### Action bar

Sits between the toolbar and the table-wrap, hidden by default:

```html
<div class="bulk-bar" role="region" aria-label="Bulk actions" hidden>
  <span class="bulk-count"><b class="bulk-count-num">0</b> selected</span>
  <div class="bulk-actions">
    <button type="button" class="btn-secondary" data-bulk-action="delete" disabled>Delete</button>
    <button type="button" class="btn-secondary" data-bulk-action="export" disabled>Export</button>
    <button type="button" class="btn-text" data-bulk-clear>Clear</button>
  </div>
</div>
```

`hidden` is a boolean HTML attribute; JS toggles it. Buttons stay `disabled`
until the backend lands — no fake submit.

### Template gate

`{% if selectable %}` controls the entire selection surface (column +
action bar). `bulk_actions_enabled` continues to gate the real action
wiring later.

## 2. CSS classes

All in `admin/base.html` `<style>`. Three new rule blocks:

```css
/* Selection column — narrow, distinct from data cells */
.table th.select-cell,
.table td.select-cell {
  width: 40px;
  text-align: center;
  padding: 0;
}
.table .select-cell input[type="checkbox"] {
  width: 16px; height: 16px;
  cursor: pointer;
  accent-color: var(--rio-accent);
}

/* Selected row — beats hover, beats zebra */
.table tbody tr.is-selected td {
  background: var(--rio-accent-bg);  /* #fff4ed */
}
.table tbody tr.is-selected:hover td {
  background: var(--rio-accent-bg);  /* hold colour, no flicker */
}

/* Bulk action bar */
.bulk-bar {
  display: flex; align-items: center; justify-content: space-between;
  background: var(--rio-bg-surface-1);
  border: 1px solid var(--rio-accent-border);
  border-radius: 8px;
  padding: 12px 16px;
  margin: 16px 0;
}
.bulk-bar[hidden] { display: none; }
.bulk-count-num { color: var(--rio-accent); font-weight: 700; }
.bulk-actions { display: flex; gap: 8px; }
```

No new tokens. Transition inherited from the v1.4.1 td rule.

## 3. JS behaviour outline

Single file: `rustio-core/assets/static/js/admin-select.js`, ~50 lines
vanilla, IIFE-scoped. Loaded via `<script src=… defer>` from `admin/base.html`.
Embedded into the binary via a new `EMBEDDED_STATIC_JS` registry (separate
from `EMBEDDED_TEMPLATES`).

**Init (DOMContentLoaded):**

1. Find every `table.table` containing `.select-all`. None → exit.
2. Per table, store a `Set<string>` of selected ids in a `WeakMap` keyed by
   the table element. No globals.
3. Skip if `data-select-init="1"` (idempotency guard for HMR / dev reloads).

**Event handlers (delegated to the table element):**

- `change` on `.row-select` → toggle id in set, toggle `.is-selected` on its
  `<tr>`, recompute header state (checked / indeterminate / unchecked),
  update bar.
- `change` on `.select-all` → for every visible `.row-select`: set checked to
  header's state, add/remove id, toggle row class. Update bar.
- `click` on `[data-bulk-clear]` → uncheck everything, clear set, remove all
  `.is-selected`, hide bar.
- (Future) `click` on `[data-bulk-action]` → set hidden `action` input value,
  submit `#bulk-form`.

**Bar update:** single function — reads set size, writes count, toggles
`hidden` on the bar.

**Click isolation:** none needed. Checkbox `<td>` is a sibling of the link
`<td>`; checkbox clicks do not traverse the link. We do *not* add a
row-level click handler.

## 4. Data flow

**Source of truth: the DOM.** The checkbox `checked` attribute IS the
selection state. The `Set<string>` is a derived cache for the count and for
fast lookup; it's recomputed from the DOM at init.

- No `localStorage`, no `sessionStorage`, no URL params.
- Page reload (search submit, pagination, filter change) → DOM resets →
  selection clears. By design, per spec.
- When backend lands: native form submit posts `selected_ids[]` directly. JS
  only sets the `action` value before submit. **No-JS fallback works
  automatically** — checkboxes are real form inputs.

**Why DOM-as-truth:** the alternative (JS Set as authoritative, sync to
DOM) introduces drift bugs when something external mutates the DOM (browser
autofill, dev-tools, browser back/forward cache). The Set-as-cache pattern
is bug-resistant and keeps the no-JS submit path intact for free.

## 5. Edge cases

| Case | Behaviour |
|---|---|
| **Pagination** | Page-scoped per spec. Header selects only visible rows. Navigating to page 2 starts fresh; page-1 selections are lost. (Cross-page selection = future RFC, would need `localStorage` or hidden-input persistence.) |
| **Empty `<tbody>`** | `{% if rows %}` already hides the table. Bar never appears. Header checkbox gets `disabled` server-side as defence-in-depth. |
| **Partial selection** | Header enters `indeterminate=true` (set via JS, not via attribute — `indeterminate` is a property, not an attribute). Re-checking selects all visible; un-checking clears all. |
| **Click link vs checkbox** | Different `<td>`s, different click targets. No row-level handler. No conflict. |
| **Click checkbox-cell whitespace** | Cell padding is 0; checkbox fills the cell. No whitespace to mis-target. (If padding is added later, wrap the input in a `<label>` whose `for=` points at the input, so the whole cell is a click target without bubbling out.) |
| **Search / filter / pagination submit** | Full page reload, DOM resets, selection clears. No stale state. |
| **Keyboard a11y** | Native checkbox: tab-reachable, space toggles. Header has `aria-label`. Indeterminate state announced by screen readers. |
| **No-JS** | Checkboxes still toggle (native). Bar stays hidden (default). When backend lands, action buttons can become real submit buttons inside the form — no-JS users get the full feature, just without the count UI. |
| **Multiple tables on one page** | `WeakMap`-keyed state isolates them. Currently only one table per list page; design doesn't lock us in. |
| **Re-init (HMR, dev template reload)** | `data-select-init="1"` flag prevents double-binding. |

## Architectural summary

**Touchpoints (5 files when implemented):**

1. `admin/list.html` — checkbox column + bulk bar markup, gated on
   `{% if selectable %}`.
2. `admin/base.html` `<style>` — `.select-cell`, `.is-selected`, `.bulk-bar`
   rule blocks.
3. `admin/base.html` — `<script src="/admin/static/js/admin-select.js" defer>` tag.
4. `assets/static/js/admin-select.js` — new file, embedded via a new
   `EMBEDDED_STATIC_JS` registry.
5. `admin/render.rs` — add `selectable: bool` to `ListCtx`, default `true` in
   `list_ctx`. Update `empty_list_ctx_skeleton` test fixture.

**One new context field, one new static asset, three new CSS rule blocks.
Generic across all models — selection is purely id-based, no field
inspection.**

## Implementation phases (sketch — to be expanded into Parts A–F when the
phase begins)

- **A.** Add `EMBEDDED_STATIC_JS` registry + the static-asset HTTP route.
- **B.** Add `ListCtx.selectable: bool`. Update render tests.
- **C.** Template + CSS surfaces in `admin/base.html` and `admin/list.html`.
- **D.** `admin-select.js` + render test that asserts the script tag and
  checkbox markup are present.
- **E.** Backend: `/admin/<model>/_action` endpoint, CSRF, permission gate,
  per-action dispatch (delete, export). Confirmation page for delete.
- **F.** Wire `bulk_actions_enabled` true and un-disable the buttons.

---

## Out of scope (will not be revisited in v1.5.0)

- Cross-page selection persistence.
- Drag-select / shift-click range selection.
- Modal confirmation UI.
- Per-action permission UX beyond the existing `perm_guard` pattern.
- Async / background bulk actions (jobs queue). Sync POST → confirm → POST is
  the v1.5.0 contract.

---

## Open questions for the implementing phase

1. Static-asset URL prefix — `/admin/static/js/` (matches CSS) or
   `/static/admin/js/`? CSS lives at `/admin/static/css/admin.css`, so the
   parallel placement is the obvious answer; confirm at implementation time.
2. Permission model for bulk delete — does the operator need
   `<model>.delete_<model>` for every selected id, or is the single
   permission check at the action endpoint sufficient? Likely the latter
   (matches single-row delete), but worth a one-line audit.
3. Empty-selection submit guard — server-side reject 400 if
   `selected_ids[]` is empty, or silently no-op? Reject 400 — surfaces a
   bug in the JS state if it ever happens.
4. CSV/JSON export streaming — chunked response or buffer-and-send? Buffer for
   v1.5.0; streaming is a v1.6+ optimization if needed.
