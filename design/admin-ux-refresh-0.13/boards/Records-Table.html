Records — Table

The workhorse. The board's argument is a sequence — page identity, then finding, then presentation, then data, then position in the set — and those five concerns are never mixed into one strip of controls.

A

Purpose

Primary task: locate a record and act on it. Secondary: understand how many there are and narrow the set. Tertiary, and far rarer: change how the list itself is composed. The screen's argument is a sequence — those three jobs are never mixed into one strip of controls.

The screen reads in five stages, and the stages never mix:

#StageAnswersContains
1Page identityWhere am I?Breadcrumb · title · one-line description · the primary record action, alone on the right
2Find / narrowWhich records am I looking for?Search · Status filter · Resource filter · Clear filters · result count, right-aligned
3View / presentationHow do I want them presented?Table | List | Cards | Compact left · passive sort statement · Set as default and Edit view right
4Data—The table
5PaginationWhere am I in the set?Showing 1–20 of N left · Previous, page numbers, Next right — attached to the table surface
  • Header. Breadcrumb, 24px title, then a 16px description line. The right side holds the primary record action and nothing else — no layout control, no filter, no view-editor action stands beside Add. It is the only strong blue on the page.
  • Rows 2 and 3 share one card, divided by a full-width 1px --border. Row 3 sits on --surface-soft because presentation is the rarer job.
  • Search 340px preferred (flexes 220–340), 38px tall, 15px/500, 17px leading icon, clear control only when the query is non-empty.
  • Active filter states it three ways: border #7890AF, fill #F4F8FD, text #174578/600. “Clear filters” renders only when something is active.
  • Result count is pushed right inside row 2, so it stays attached to the filtering group it describes and never sits near Add.
  • Table 40px header, 48px minimum rows, 16px cell padding, 1px dividers, hover --surface-soft, no zebra. Pagination is inside the same card.

Column order tells the record's story left to right: identity → primary related context → state → time → actions. For Assignment that is Booking → Resource → Status → Accepted at → Actions. The technical id does not lead the row, because it is not this record's human identity. Service type and duration ride under the resource as in-cell detail at 14px/500 #3F4A59, keeping five columns instead of seven.

D · F

Proposals and product status

Five-stage page order, two operational rows

Page identity → find → present → data → pagination. Finding and presentation occupy separate rows of one card, divided by a full-width rule, with the quieter ground under the presentation row. Pure composition of controls that already exist.

Visual / UX only

The header holds the primary record action alone

No layout control, filter or view-editor action beside Add. A one-line description sits under the title so the page states its own job.

Visual / UX only

Semantic column order; identity first

Identity → related context → state → time → actions. The technical id stops leading the row. Low-value columns fold into the cell above them as secondary detail rather than claiming a column.

Visual / UX only

Search reads as the first thing in the operational bar

340px preferred, 38px tall, 15px/500 value, 17px leading magnifier, and a clear control that appears only when the query is non-empty and submits the same form with q emptied. Presentation over the existing ?q=.

Visual / UX only

Active filters state it three ways

Border, fill and weight — colour is never the only signal. “Clear filters” appears only when something is active, and the result count names how many filters are on.

Visual / UX only

Passive sort statement, not a second control

“Sorted by Accepted at · newest first” at 14px/500 beside the layout switch. It reports the state the headers set. There is deliberately no sort-by dropdown in Table mode.

Visual / UX only

Row Delete carries the destructive semantic

Both row actions keep text labels; neither is icon-only. Delete leads to the confirmation page, whose submit is also the danger face.

Visual / UX only

Pagination attached to the data it pages

Inside the table card, below the rows: range left; Previous, page numbers, Next right at 14px/600 with 38px targets. Disabled arrows stay visible and disabled so the control does not change width.

Visual / UX only

Two distinct empty states

“No assignments yet” (with the create action) and “No assignments match these filters” (with Clear filters) are different situations and do not share copy.

Visual / UX only

Sortable column headers

The header cell is the sort control for columns already marked sortable. Uses the existing sort / dir contract and ColumnView.sortable — the header builds the same URL the current control builds. This is a second presentation of the existing sort, not a second sorting system. A column with sortable = false, including every merged column, renders as plain text.

Backend wiring

Individually removable active filters

Each active constraint can be dropped on its own without clearing the rest. The active filter state and clear_filters_href already exist; this needs one href per constraint that drops a single parameter and keeps the others — the same query-string builder that already produces the layout links.

G

Responsive contract

WidthResult
1920Main at the 1600px cap. Both operational rows stay single rows; search keeps its 340px and does not stretch. The table fills the width without a scroller and the actions column is on screen.
1440Full desktop composition, identical structure.
900Row 2 wraps: search and filters on the first line, the result count stays attached beneath them rather than migrating to another group. Row 3 keeps the layout switch left and moves the view tools to their own line. Type sizes unchanged.
390Each stage stacks vertically in the same order. Search full width, filters full width, count below them, layout switch scrolls horizontally inside its own group, view tools full width. Table scrolls inside its card with Booking first. No type size is reduced.

There is no automatic Table → Cards switch at any width. The layout is whatever the operator chose or the view's stored default; the runtime does not swap it for them, and this design does not claim it does.

H

Visual acceptance

  • The page reads top-to-bottom as identity → find → present → data → pagination, and the five stages are visually separable at a glance.
  • Add stands alone in the header. No filter, layout control or view-editor action sits beside it.
  • Search and filters read as one operational group; the result count is attached to that group, not to Add.
  • Layout switch and view tools read as a separate group on their own row, on a quieter ground.
  • Exactly one strong blue action on the page, and it is Add.
  • The first column anchors the record's identity — a booking number, not a database id.
  • Row actions are right-aligned and visually subordinate; both carry text labels.
  • Table header is 40px, rows at least 48px, cells 16px horizontal padding.
  • Cells 15px/500 #171B22; in-cell detail 14px/500 #3F4A59. Nothing operational is faint.
  • No functional text below 13px anywhere on the board, at any width.
  • Pagination sits below the data on the table surface; no rows-per-page control appears.
  • No bulk-selection checkbox appears anywhere on the approved board.
  • No horizontal document overflow at 390.
